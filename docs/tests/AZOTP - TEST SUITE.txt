ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnpqrstuvwxyz123456789

============================================================
XVIII. IMPLEMENTATION RISK SURFACE (NON-SPEC)
============================================================

This section defines CRITICAL implementation risks that are
NOT protocol design flaws, but WILL break AZOTP security
guarantees if mishandled.

These risks are MANDATORY to mitigate.

------------------------------------------------------------

1. NON-ATOMIC DATABASE OPERATIONS

RISK:

- race conditions during verification
- multiple successful OTP validations

REQUIREMENTS:

- verification MUST run inside a transaction
- MUST use SELECT FOR UPDATE (or equivalent locking)
- MUST ensure atomic mutation of:
  - used flag
  - attempt state

FAILURE RESULT:

→ MULTIPLE SUCCESSFUL AUTHENTICATIONS
→ REPLAY POSSIBLE
→ SYSTEM INVALID

------------------------------------------------------------

2. INCORRECT CONSTANT-TIME COMPARISON

RISK:

- timing side-channel leakage
- OTP inference via latency attacks

REQUIREMENTS:

- MUST use constant_time_equal
- MUST operate on fixed-length byte arrays
- MUST NOT use:
  - ==
  - early return comparisons

FAILURE RESULT:

→ OTP LEAKAGE
→ PREDICTION ATTACKS POSSIBLE
→ SYSTEM INVALID

------------------------------------------------------------

3. INCONSISTENT CANONICALIZATION ACROSS SERVICES

RISK:

- different byte sequences for identical logical input
- OTP mismatch between services

REQUIREMENTS:

- MUST enforce identical canonical encoding across systems
- MUST use UTF-8 byte-length consistently
- MUST NOT:
  - trim inputs
  - normalize canonical_context field strings
  - mutate values
- MUST share identical formatting logic across languages

FAILURE RESULT:

→ VALID OTP REJECTED
→ CROSS-SERVICE FAILURE
→ SYSTEM INVALID

------------------------------------------------------------

4. WEAK RANDOMNESS IN NONCE

RISK:

- nonce predictability
- replay or precomputation attacks

REQUIREMENTS:

- MUST use CSPRNG
- MUST ensure nonce uniqueness per challenge
- MUST enforce single-use nonce
- MUST NOT reuse nonce under ANY condition

FAILURE RESULT:

→ REPLAY ATTACK POSSIBLE
→ BINDING BREAK
→ SYSTEM INVALID

------------------------------------------------------------

5. TIME DRIFT NOT ENFORCED

RISK:

- inconsistent time_bucket calculation
- false acceptance or false rejection

REQUIREMENTS:

- MUST synchronize clocks using NTP
- MUST enforce drift ≤ ±30 seconds
- MUST ensure consistent time source across all services

FAILURE RESULT:

→ OTP VALIDATION FAILURE
→ CROSS-SERVICE INCONSISTENCY
→ SYSTEM INVALID
